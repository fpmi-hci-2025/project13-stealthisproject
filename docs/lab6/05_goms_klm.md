# Этап 5. Анализ интерфейса по моделям GOMS и KLM

## 1. Метод GOMS (Goals, Operators, Methods, Selection rules)

Для анализа выбраны 3 формы веб-приложения. Рассчитаем время выполнения для двух методов ввода: **Мышь (Mouse)** и **Клавиатура (Keyboard/Tab)**.

**Параметры операторов (CMN-GOMS):**
*   **K** (Keystroke/Keypress): 0.2 с (опытный пользователь)
*   **P** (Point with mouse): 1.1 с
*   **H** (Home - перемещение руки): 0.4 с
*   **M** (Mental preparation): 1.35 с
*   **B** (Button click): 0.1 с

### Форма 1: Вход в систему (Login)
*Поля: Email, Пароль. Действие: Кнопка "Войти".*

**Вариант А: Преимущественно мышь**
1.  H (рука на мышь): 0.4
2.  P (курсор на Email): 1.1
3.  B (клик): 0.1
4.  H (рука на клавиатуру): 0.4
5.  M (вспомнить email): 1.35
6.  K*15 (ввод email): 3.0
7.  H (рука на мышь): 0.4
8.  P (курсор на Пароль): 1.1
9.  B (клик): 0.1
10. H (рука на клавиатуру): 0.4
11. M (вспомнить пароль): 1.35
12. K*8 (ввод пароля): 1.6
13. H (рука на мышь): 0.4
14. P (курсор на кнопку Войти): 1.1
15. B (клик): 0.1
**Итого:** ~12.9 сек

**Вариант Б: Клавиатура (Tab)**
1.  (Курсор уже в поле Email)
2.  M (вспомнить email): 1.35
3.  K*15 (ввод email): 3.0
4.  K (Tab): 0.2
5.  M (вспомнить пароль): 1.35
6.  K*8 (ввод пароля): 1.6
7.  K (Enter): 0.2
**Итого:** ~7.7 сек

**Вывод:** Вариант с клавиатурой эффективнее на ~40%.

### Форма 2: Поиск рейса
*Поля: Откуда, Куда, Дата. Действие: Найти.*

**Расчет (Упрощенно для варианта с Tab):**
*   M (подготовка) + K*6 (Минск) + K (Tab) + K*5 (Брест) + K (Tab) + K*10 (Дата) + K (Enter).
*   1.35 + 1.2 + 0.2 + 1.0 + 0.2 + 2.0 + 0.2 = **6.15 сек**.

**Расчет (Мышь - выбор из выпадающих списков):**
*   P (поле Откуда) + B + P (выбор Минск) + B + P (поле Куда) + B + P (выбор Брест) + B + P (календарь) + B + P (дата) + B + P (кнопка) + B.
*   (1.1+0.1)*7 + M(поиск глазами)*3 = 8.4 + 4.05 = **12.45 сек**.

### Форма 3: Данные пассажира
*Поля: Фамилия, Имя, Паспорт. Действие: Сохранить.*

**Вариант Б (Клавиатура):**
*   M + K*7 (Ivanov) + K(Tab) + K*4 (Ivan) + K(Tab) + K*9 (Passport) + K(Enter).
*   1.35 + 1.4 + 0.2 + 0.8 + 0.2 + 1.8 + 0.2 = **5.95 сек**.

## 2. Метод KLM (Keystroke-Level Model) для мобильного приложения

Для мобильных интерфейсов адаптируем операторы:
*   **T** (Tap/Touch): 0.3 с (аналог клика, но быстрее так как не нужно точное позиционирование курсора, если элементы крупные).
*   **S** (Swipe): 0.5 с.
*   **K** (Virtual Keyboard Tap): 0.3 с.
*   **M** (Mental): 1.35 с.

### Задача 1: Мобильный логин
1.  T (поле Email): 0.3
2.  M (подготовка): 1.35
3.  K*15 (ввод): 4.5
4.  T (Next field): 0.3
5.  K*8 (пароль): 2.4
6.  T (Button Login): 0.3
**Итого:** **9.15 сек** (медленнее физической клавиатуры из-за скорости набора на экране).

### Задача 2: Выбор даты (Скроллер/Барабан iOS)
1.  T (открыть календарь): 0.3
2.  M (найти число): 1.35
3.  S (скролл дней): 0.5
4.  S (скролл месяцев): 0.5
5.  T (Подтвердить): 0.3
**Итого:** **2.95 сек** (быстрее, чем ввод даты вручную 10.10.2025).

### Задача 3: Удаление билета из корзины (Swipe to delete)
1.  M (найти билет): 1.35
2.  S (свайп влево): 0.5
3.  T (кнопка Удалить): 0.3
**Итого:** **2.15 сек**.

## 3. Общий вывод по моделированию
1.  **Desktop:** Навигация с помощью клавиатуры (Tab-индекс) критически важна для форм ввода данных пассажиров, так как ускоряет процесс почти в 2 раза. Необходимо убедиться, что атрибуты `tabindex` расставлены корректно.
2.  **Mobile:** Использование нативных элементов управления (барабаны дат, свайпы) значительно ускоряет взаимодействие по сравнению с вводом текста. Рекомендуется использовать нативные дейтпикеры вместо текстовых полей.
